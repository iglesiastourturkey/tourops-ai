Fix the custom TourPilot sign-in flow to correctly support Clerk Client Trust.

Current production issue:

A super_admin can sign in successfully from an already trusted computer.

When the exact same valid account/password is used from a new computer, Clerk returns:

needs_client_trust

The current custom admin login page treats this as an error and displays:

"Giriş tamamlanamadı (durum: needs_client_trust). Lütfen tekrar deneyin."

This is incorrect.

Root cause:
Clerk Client Trust requires additional verification on a new device, but our custom sign-in flow does not handle the needs_client_trust state.

Do not disable Clerk Client Trust.
Do not weaken authentication security.
Do not bypass second-factor/client-trust verification.

Implement proper support for it.

Requirements:

1. Existing password login

Keep the existing:

- email or username
- password

flow.

After the password attempt inspect the Clerk sign-in status.

Handle at minimum:

- complete
- needs_client_trust
- needs_second_factor
- needs_new_password

Do not treat these expected Clerk states as generic errors.

2. needs_client_trust

When Clerk returns:

needs_client_trust

inspect supportedSecondFactors.

Prefer verification in this order where supported:

1. email_code
2. phone_code
3. email_link

For email_code:

- call Clerk prepareSecondFactor() correctly
- show a second UI step on the same login page

Field:
"Doğrulama Kodu"

Buttons:
"Doğrula"
"Kodu Yeniden Gönder"
"Geri"

Do not reveal more of the destination email/phone than Clerk already safely provides.

3. Verification

When the user enters the code:

- use Clerk's supported second-factor verification API
- verify the code
- if signIn.status becomes complete:
  - call setActive using createdSessionId
  - continue through the existing TourPilot profile/role loading flow
  - redirect according to the existing role logic

For super_admin/admin:
→ /dashboard

Preserve existing role redirects for all other roles.

4. needs_second_factor

The application may also encounter normal MFA.

Do not break it.

Handle needs_second_factor separately from needs_client_trust.

If TOTP, SMS, email code, or another supported factor already exists, show the appropriate verification state.

Reuse common verification UI where practical.

5. needs_new_password

Preserve the existing temporary-password / first-login password-change behavior.

Do not allow Client Trust handling to bypass mustChangePassword.
