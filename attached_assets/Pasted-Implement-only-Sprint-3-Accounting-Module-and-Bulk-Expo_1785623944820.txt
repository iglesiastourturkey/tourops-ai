Implement only Sprint 3: Accounting Module and Bulk Export System for TourPilot.

Goal:
Create a practical tourism-operation accounting workflow that collects income, expenses, receipts and invoices in one place, links them to operations/customers/suppliers, and allows accounting users or managers to export complete records as PDF, Excel and ZIP packages.

Do not attempt to build a legally complete Turkish accounting/ERP system. This is an operational finance and document-management module.

Roles and access:
- super_admin: full access
- admin: full operational finance access
- accounting: full accounting module access
- operations: can view operation-level financial summaries and submit documents, but cannot approve accounting records
- guide: can only add/view receipts related to their assigned operations
- all permissions must be enforced in backend APIs, not only hidden in the UI

1. Navigation and pages

Add a role-aware “Muhasebe” navigation item for:
- super_admin
- admin
- accounting

Create these pages:

/accounting
- accounting dashboard

/accounting/transactions
- all income and expense records

/accounting/documents
- receipt and invoice review queue

/accounting/reports
- filters and bulk exports

/accounting/operations/:operationId
- complete accounting file for one operation

Do not expose these pages to guides.

- transactionDate
- dueDate nullable
- paidAt nullable
- description nullable
- documentNumber nullable
- customerId nullable FK
- supplierId nullable FK
- tourId nullable FK
- operationId nullable FK
- receiptId nullable FK
- createdByProfileId
- approvedByProfileId nullable
- approvedAt nullable
- rejectionReason nullable
- createdAt
- updatedAt

Required document fields:
- id
- documentType: receipt | invoice | expense_note | other
- operationId nullable

- supplierId nullable

- mimeType

Reuse existing operation_receipts wherever possible.

- operation

Accounting users can:

11. Safety and integrity

- Confirmation required before rejecting or deleting pending records
- Approved financial records should not be hard-deleted
- Use archive/cancel or reversal logic for approved records
- Prevent duplicate transaction creation from the same receipt
- Validate positive amounts
- Validate supported currencies
- Return Turkish HTTP 409 warnings for linked/duplicate/conflicting records
- Record who created and approved each financial record
- Protect all export endpoints with RBAC
- Do not return files belonging to unauthorized operations
